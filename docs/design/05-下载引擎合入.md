# 下载引擎合入：`lib_common` → `lib_download`

> 决策来源：用户指示「对于下载功能你可以合入 `GGEC-Android-EarBuds` 的 `lib_common` 库，然后使用下载功能」。
> 本文记录**怎么合、合了什么、没合什么、怎么用**。

## 1. 合入策略：只摘下载子系统，不搬整个库

`lib_common` 共 **203 文件 / 19,650 行**，包含文件、SAF、权限、刷新率、保活、日志、分享等大量与本工程
无关的能力，且依赖 `androidx.activity/appcompat/material/documentfile/lifecycle`。

下载相关代码是**自包含**的（`download/**` + 少量工具），因此只摘这一部分：

| 来源 | 去向 | 文件 | 行 |
| --- | --- | --- | --- |
| `com/yovo/lib_common/download/**` | `com/yohu/lib_download/**` | 34 | 3,830 |
| `internal/util/FileNames.java`、`IoUtil.java` | `com/yohu/lib_download/util/` | 2 | — |
| `log/YoLog.java`（依赖整套日志子系统） | 自写**最小垫片**（只 `d/i/w/e`） | 1 | 102 |
| 合计 | 新模块 `lib_download` | **37** | **4,004** |

包名统一按本仓库约定改为 `com.yohu.*`（原 `com.yovo.*` 已清零，脚本校验过）。

## 2. 没合什么，为什么

| 不合入的内容 | 原因 |
| --- | --- |
| `lib_common.system.file`（SAF/路径/URI 文件管理，约 4,000 行） | 本工程的落盘目录由 `app` 用自己的私有目录，不需要 SAF 抽象 |
| `lib_common.system.download`（系统 DownloadManager 封装） | 与分块断点下载器功能重叠；本工程要的是可控的分块下载 |
| `lib_common.log.*`（约 3,000 行日志子系统） | 下载只用到 4 个方法，为此拖入整套日志不值得 |
| `lib_common.system.permission / refresh_rate / keepalive / share` | 与本工程无关 |
| `androidx.activity/appcompat/material/documentfile/lifecycle` | 下载子系统实际只需要 `androidx.annotation` + `androidx.core`（`NotificationCompat`） |

结果：`lib_download` 运行时依赖只有 `androidx.annotation` 与 `androidx.core`，**没有** OkHttp/Gson/Retrofit，
与 `lib_urlparse` 的「零第三方运行时依赖」口径一致。

## 3. 架构位置

```
app
 ├── ui
 ├── task/DownloadRunner         ← 队列 / 并发 / 暂停继续 / 等网络 / 自动续传（见 07）
 ├── download/DownloadPipeline   ← 一次解析结果 → 一组文件（直链 / HLS / DASH 合并 / 校验）
 │     └── AssetDownloader       ← 桥接：MediaAsset → YoDownload.Request
 ├── lib_urlparse（纯 JVM 可测，只解析不下载）
 │     └── api / spi / core / util / sniff / rules / provider / fetch
 └── lib_download（Android）
       └── YoDownload（门面）+ 分块断点引擎 + SQLite 断点表
```

**为什么下载不放进 `lib_urlparse`**：下载需要 `Context`、SQLite 断点、系统通知、`ConnectivityManager`，
放进纯 JVM 模块会立刻破坏「核心可在 JVM 上测」这条底线（也是旧实现最大的结构问题）。
所以下载作为**同级模块**，由 `app` 装配。

## 4. 怎么用

```java
// 1) 初始化（进程内一次，UrlDownApp.onCreate 里做）
AssetDownloader.init(context, DownloadRunner.downloadDir(context));

// 2) 下载一条解析出来的媒体；requestId 固定（任务 key + 序号），同一 ID 再 start 即续传断点
AssetDownloader.start(requestId, asset, dir, "标题_1.mp4", new AssetDownloader.Callback() {
    @Override public void onProgress(long done, long total, long speed, long etaMs) { /* 更新进度 */ }
    @Override public void onSuccess(File file) { /* 校验 / 合并 */ }
    @Override public void onPaused() { /* 停在断点 */ }
    @Override public void onCanceled() { }
    @Override public void onError(DownloadError error, String detail) { /* 分类后的失败，如实提示 */ }
});

// 3) 暂停 / 取消 / 丢弃断点
AssetDownloader.pause(requestId);
AssetDownloader.cancel(requestId);
AssetDownloader.forget(requestId, true);
```

`AssetDownloader` 只做映射与错误分类：**不解析、不推导文件名、不做调度**。这样下载引擎替换时只改一个文件。
实际调用方是 `download/DownloadPipeline`，界面不直接碰它。

## 5. 下载引擎能力（合入即得）

| 能力 | 说明 |
| --- | --- |
| 分块并行 | `maxBlocksPerTask`（当前 3）；支持 `Range` 的服务器会分块拉取 |
| 断点续传 | SQLite 断点表 `BreakpointInfo` / `BlockInfo`；进程重启后可恢复 |
| 暂停/恢复/取消/移除 | `YoDownload.pause/resume/cancel/remove` |
| 重试 | `maxRetryCount`（当前 2），配合网络类型约束 |
| 进度 | `downloadedBytes / totalBytes / speedBytesPerSecond / etaMillis / percent` |
| 并发控制 | 引擎 `maxParallelTasks` 放宽到 4；实际并发由 `DownloadRunner` 按设置“同时下载”（1–3）控制 |
| 通知 | 引擎内置通知未启用；改由 `task/DownloadService` 前台服务出一条汇总通知 |
| 线程 | 回调默认切回主线程（`autoCallbackToMainThread`） |

## 6. 在引擎之上补的（`app`）

合入的引擎只负责"单 URL 分块下载"。播放列表、音视频分离、命名、校验和任务管理在 `app` 里补齐：

| 能力 | 位置 | 说明 |
| --- | --- | --- |
| M3U8（含 AES-128、fMP4 MAP、字节范围） | `download/hls/HlsDownloader` | 分片级断点续传；播放列表变了从头下；直播流拒绝 |
| DASH 合并 | `download/DashMuxer` | 系统 `MediaMuxer`，音视频分别下完再合并 |
| 命名 | `download/MediaFileNames` | 真实扩展名白名单，拒绝 `~tplv-noop.image` 类伪扩展 |
| 落盘校验 | `download/ContainerProbe` | 字节数 + 容器签名，拦截页判 `NOT_MEDIA` |
| 失败分类 | `download/DownloadError` | 引擎异常 / HTTP 状态 → 一句用户能懂的话 + 是否可重试 |
| 进度继承 | `lib_download` `DownloadCore.inheritProgress` | 续传时把已下字节算进进度，不从 0% 重新涨 |
| 任务调度 | `task/DownloadRunner` + `DownloadService` | 暂停 / 继续 / 等网络 / 自动续传 / 前台通知，见 07 |
