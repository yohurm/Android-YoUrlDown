# 迁移计划、风险与未决问题

## 1. 迁移原则

1. **旧仓库不动**：`DownLoadAnalysis` 保持可运行，作为证据源与对照基线（它承载 30 个文件的真机
   sha256 证据链）。迁移是"复制 + 改造"，不是"搬走"。
2. **分批可验**：每批结束必须有：编译通过 + 新增单测通过 + 目标平台真机复验（沿用旧报告口径）。
3. **先骨架后血肉**：先落 `api`/`spi`/`core` 与判据，再逐平台迁 provider，最后接 UI。
4. **不破坏证据链**：任何一批若导致某平台回退，先修再进入下一批。

## 2. 批次划分

| 批次 | 内容 | 产出 | 验收 |
| --- | --- | --- | --- |
| B0（已完成） | 仓库骨架 + 构建配置对齐 | `app` / `lib_urlparse` 可编译 | `:app:assembleDebug` 通过 |
| B1 | `api` + `spi` + `util` + `sniff` 移植，边界校验任务 | 空引擎可实例化，判据单测通过 | `test` 绿 + 三个边界任务绿 |
| B2 | `fetch` + `core`（注册表/调度/trace） | 调度语义单测（含优先级、失败重试、兜底） | 调度单测绿 |
| B3 | `rules` 全量移植（11 组） | 规则单测 + 真实固件样本 | 规则单测绿 |
| B4 | 第一批 provider：B站、微博、小红书、今日头条 | 4 平台 JVM 单测（假 HTTP） | 4 平台单测绿 |
| B5 | 第二批 provider：抖音（webpage + webview.js）、公众号、微视、皮皮虾、快手、Instagram、视频号、cloud、sniffer | 全部通道就位 | 通道单测绿 |
| B6 | 下载子系统（M3U8、命名、容器校验；后移到 `app/download`，见 02 §9） | 下载单测（本地 HTTP + 临时目录） | 下载单测绿 |
| B7 | `app` 适配器（WebView / DASH / 落盘）+ UI 接入 | 真机可跑通单平台 | 单平台真机闭环 |
| B8 | 12 平台矩阵复验 + 证据重建 | 新报告 | 8/12 通过，4 个如实标注 |

## 3. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| provider 迁到纯 JVM 后行为漂移 | 某平台解析结果与旧实现不一致 | B4/B5 每批都用**旧实现抓取的真实响应固件**做对照断言 |
| `DashMuxer` 外置后 B站产物异常 | B站闭环失败 | B7 用真机复验 156 MB 产物；容器与时长双校验 |
| WebView 线程约束被破坏 | 偶发崩溃/超时 | 契约里写死线程亲和 + 注入时校验 + 适配器单测 |
| 规则里出现密钥字面量 | 合规风险 | `checkNoSecrets` 任务 + 人工复核 |
| 平台侧页面改版 | 单测固件失效 | 固件按"抓取时间"标注，改版时用新固件替换而不是放宽断言 |
| 迁移期间旧仓库被误改 | 证据链失真 | 旧仓库只读使用，不在其中改代码 |

## 4. 待用户决策（阻塞后续实现，但**不阻塞**本设计）

| 编号 | 问题 | 备选 | 建议 |
| --- | --- | --- | --- |
| D1 | `lib_urlparse` 是否允许引入 **OkHttp**？ | 继续用 `java.net`（零依赖）/ 引 OkHttp | 先零依赖（可审计、体积小）；若 M3U8/下载需要连接复用再评估 |
| D2 | 是否保留 **Rhino** JS 求值器（旧实现有 `RhinoJsEvaluator`）？ | 保留 / 只保留 WebView 求值 | 优先只保留 WebView；Rhino 需额外依赖且与"零依赖"冲突 |
| D3 | DASH 合并是否需要支持 **后台任务/断点续传**？ | 否（仅前台）/ 是 | 先否，产品需求明确后再加。**已调整**：下载改由前台服务承载并支持暂停 / 续传（见 07） |
| D4 | `sniff` 判据是否对外公开（供第三方接入自己的下载器）？ | 不公开 / 公开 | 不公开；如需要，另开 `spi.MediaClassifier` |
| D5 | 是否要求 **`app` 之外**的调用方（如其他产品线）复用 AAR？ | 只自用 / 对外发布 | 只自用；发布则需要 `api`/`spi` 稳定承诺与语义化版本 |
| D6 | 平台范围是否锁定旧报告的 12 个？ | 锁定 / 扩展 | 锁定 12 个；新增平台按 `ParseProvider` 扩展，不改引擎 |

## 5. 现在明确**不做**的事

- 不实现"绕过验证码/风控"的能力（快手需滑动验证；这是服务端策略，不做对抗）。
- 不扫描其它 App 的私有数据目录（旧实现依赖 root，属于跨应用数据读取，不在本工程设计范围内）。
- 不内置任何第三方解析服务的地址与凭据。
- 不在 `lib_urlparse` 里做 UI、权限申请、文件选择器。

## 6. 完成定义（Definition of Done）

设计阶段的完成定义是**可执行**，而非"文档写完"：

1. 本文档 + 01/02/03 三份设计经用户确认（含 §4 决策项）。
2. B1 批次的边界校验任务可运行，且能对**故意越界**的代码报错（先验证任务有效，再写业务代码）。
3. 每一批都有对应单测与（适用的）真机证据，口径与旧报告一致。
